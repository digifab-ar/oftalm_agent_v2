1. Vista general del sistema

2. Modos de turno (bootstrap | respuesta)

Calculado en detectarModoTurno(estado) antes del intérprete. El modo viaja en el user prompt de protocolo, auditor y comunicación (no en schemas JSON).

Modo Disparador Intérprete Protocolo / auditor Notas
bootstrap Ojo activo con letraActual, logmarActual y logmarFinal en null (tras POST /api/examen/nuevo) Omitido — interpretacionBootstrap(): continuacion Inicio clínico del ojo: H@0.3, foróptero + TV Primer POST /turno {} ejecuta bootstrap automáticamente. Frase social del paciente se loguea, no se interpreta.
respuesta Ojo ya inicializado LLM con estimulo de fase (lib/estimulo.js) Flujo estándar según clasificación Endpoints HTTP sin cambios.

2.2 Fallbacks (mitigación pipeline)

Tres caminos distintos si el auditor rechaza tras reintentos o falla el bootstrap. El motivo queda en detalleEvento.motivo.

Función Cuándo Mensaje al paciente (ej.) motivo
fallbackBootstrap() modo === bootstrap y auditor falló “Hubo un problema al iniciar el examen…” fallback_bootstrap
fallbackAuditoria() modo === respuesta, clasificación clara (correcta, incorrecta, no_ve) “Un momento, estoy ajustando el examen. Mirá la pantalla…” fallback_auditoria
fallbackAuditoria() / repregunta Auditor falló y clasificación no clínica “No llegué a entender bien la letra…” (como ambigua) fallback_auditoria
Regla de mitigación: no decir “no entendí la letra” cuando el paciente fue entendido clínicamente pero falló la validación del protocolo (evita desalinear TV y mensaje).

ActividadDetalle
Clasificacionescorrecta, incorrecta, no_ve, ambigua, confianza_baja, frase_paciente_no_clinica, continuacion

5.2 Protocolo

ActividadDetalle
BootstrapInicio ojo: RX, oclusión, H@0.3, contadores en 0
Correctaaciertos += 1; si ≥ 2 → cierre (sin TV extra en ese ojo)
Contador = 1Bajar logMAR + rotar letra + obligatorio tv
Cierre RMismo turno: cierre_ojo_R_e_inicio_L + foróptero + TV H@0.3
Ambigua / confianza_bajaacciones: [], repregunta_sin_cambio
Orden MQTTForóptero → TV

5.3 Auditor

ActividadDetalle
Estructural (core)Separar rol intérprete vs protocolo; orden acciones; ambigua sin MQTT

no_ve / incorrectaSubida ≤1 paso + tv; no incrementar aciertosPorLogmar; ignorar confirmaciones
BootstrapValidar inicio H@0.3 + acciones esperadas

7. Flujos de datos

7.1 Turno bootstrap (ej. T0 post-/nuevo)

Voz: POST /turno {}
  → detectarModoTurno → bootstrap
  → interpretacionBootstrap (continuacion)
  → Protocolo (modo bootstrap): inicio R, H@0.3, acciones
  → Auditor (modo bootstrap): aprueba
  → Comunicación: "Mirá la pantalla…"
  → patch + MQTT + pasos[]

7.2 Turno respuesta (paciente habló)

Voz: respuestaPaciente + confianza
  → detectarModoTurno → respuesta
  → Intérprete: clasificacion (+ estimulo fase)
  → Protocolo → Auditor (≤1 retry)
  → [aprobado] Comunicación (huboCambioDispositivo)
  → [fallo auditor] fallbackAuditoria | fallbackBootstrap
  → patch + MQTT → pasos[] + contextoVoz

8. Separación de responsabilidades

DecisiónResponsable
¿Modo bootstrap o respuesta?detectarModoTurno (código)
¿Qué dijo el paciente?Intérprete (solo modo respuesta)
¿logMAR, ojos, MQTT?Protocolo (fase agudeza)
¿Propuesta válida?Auditor
¿Texto y esperar respuesta?Comunicación (o fallback)
¿Transcripción al servidor?Oftalmólogo Virtual
¿Persistir y publicar?Servidor
