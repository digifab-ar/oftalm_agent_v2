1. Vista general del sistema

El examen se divide en dos capas:

Capa Componente Responsabilidad
Voz (cliente) chatAgent — Oftalmólogo Virtual Conversar con el paciente, transcribir audio literal, llamar al backend vía consultarExamen. No interpreta clínica ni controla dispositivos.
Backend Pipeline en procesarTurnoPipeline Cuatro agentes LLM en cadena + aplicación de estado y MQTT.

El agente de voz solo recibe del backend: pasos[].mensaje, contextoVoz y ok. El razonamiento interno no se expone al paciente.

2. Orden de ejecución

2.1 Por turno en el backend (procesarTurnoPipeline)

Paso Agente / acción Condición Qué ocurre después
0Cargar estadoSiempreestadoAntes = obtenerEstadoParaOrquestador()
1IntérpreteSiempreClasificación lingüística (respuestaPaciente + confianza)
2ProtocoloSiempre (1.ª vez)Propuesta: estadoPatch, acciones, evento
3AuditorTras cada propuestaAprueba o rechaza
3bProtocolo (reintento)Auditor rechaza y reintentos < 1Protocolo recibe feedback con violaciones
4aComunicaciónAuditor aprobóMensajes al paciente + contextoVoz
4bFallbackAuditor rechazó tras reintentosRepregunta fija (sin LLM comunicación)
5ServidorSiemprePatch → MQTT → historial
6Respuesta HTTPSiemprepasos, contextoVoz, traza opcional

Intérprete → Protocolo → Auditor → [patch + MQTT] → Comunicación

El bucle protocolo ↔ auditor permite como máximo 1 reintento (MAX_REINTENTOS_PROTOCOLO = 1).

6. Flujo de datos en un turno típico

Paciente habla
    → Voz: respuestaPaciente + confianza
        → Intérprete: clasificacion (+ letraElegida si aplica)
            → Protocolo: estadoPatch + acciones + evento
                → Auditor: aprobado?
                    → [si no] Protocolo con feedback (máx. 1 vez)
                    → [si sí] Comunicación: mensajesPaciente + contextoVoz
            → Servidor: patch estado + MQTT + historial
    → Voz: lee pasos[].mensaje según contextoVoz

Caso excepcional: auditor rechaza tras reintento → fallback repregunta sin MQTT.
